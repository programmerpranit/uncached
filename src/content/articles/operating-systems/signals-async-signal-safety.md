> [!KEY]
> **TL;DR.** A **signal** is an asynchronous notification sent to a process or thread: Ctrl-C (`SIGINT`), a stop request from systemd or Kubernetes (`SIGTERM`), a child exiting (`SIGCHLD`), a write to a closed socket (`SIGPIPE`), a bad memory access (`SIGSEGV`). The kernel delivers it on the thread's next return to user mode by **pushing a handler frame onto the stack**, so the handler runs **between any two instructions** of your program: in the middle of `malloc`, `printf`, or a half-finished data structure update. Calling those same functions from the handler can **deadlock** (the interrupted code holds their lock) or **corrupt state**. POSIX therefore lists a small set of **async-signal-safe** functions (`write`, `_exit`, `kill`, `sigaction` and a few dozen more), and nothing else should be called in a handler. The robust pattern is to **do almost nothing in the handler**: set an atomic flag, write a byte to a pipe, or avoid handlers entirely with `signalfd` or a `sigwait` thread, and do the real work (shutdown, reload, log rotation) in normal code. Also: `SIGKILL` and `SIGSTOP` can't be caught, same-type signals don't queue, and PID 1 in a container ignores signals it has no handler for.

## The problem: interrupting a program from outside

The kernel and other processes need a way to poke a running program: "the user pressed Ctrl-C", "please shut down", "your child exited", "you just dereferenced a bad pointer". Unix signals, dating back to early Unix, are that mechanism: small numbered notifications with default actions, which programs can override with handlers.

They're simple to send (`kill -TERM <pid>`) and notoriously hard to handle correctly.

## How signals are delivered

![Six steps: a signal is generated by kill, Ctrl-C, a child exit or a fault; it is marked pending; on the next return to user mode the kernel checks; it pushes a handler frame onto the user stack; the handler runs at any instruction of the interrupted code; sigreturn restores registers and the code resumes, or the syscall gets EINTR.](/figures/signals/delivery.svg "The kernel borrows the thread for the handler, wherever it happened to be.")

1. **Generation.** By another process (`kill()`), the terminal driver (Ctrl-C sends `SIGINT`, Ctrl-Z sends `SIGTSTP`), the kernel (child exit → `SIGCHLD`, broken pipe → `SIGPIPE`, timer → `SIGALRM`), or a hardware fault in the thread itself (`SIGSEGV`, `SIGBUS`, `SIGFPE`).
2. **Pending.** The signal is recorded in a pending set, per thread or per process. **Blocked** signals (in the thread's signal mask) stay pending until unblocked.
3. **Delivery** happens when the thread returns from kernel to user mode (after a system call, interrupt or timer tick). A process-directed signal goes to any thread that doesn't block it.
4. **Default action**, if no handler is installed: terminate, terminate with a core dump, stop, continue, or ignore.
5. **Handler:** the kernel saves the thread's registers in a **signal frame** on the user stack (or an alternate stack set with `sigaltstack`) and jumps to the handler. When it returns, `sigreturn` restores the registers and the program continues exactly where it was.
6. **Interrupted system calls:** if the thread was blocked in a slow system call (`read` on a socket, `accept`, `sleep`), the call fails with **`EINTR`**, unless the handler was installed with `SA_RESTART`, in which case many calls restart automatically.

A few rules:

- **`SIGKILL` and `SIGSTOP`** can't be caught, blocked or ignored. That's what makes `kill -9` reliable, and why it gives no chance to clean up.
- **Standard signals don't queue.** If `SIGCHLD` arrives twice while pending, the process sees it once, so a handler must reap children in a loop (`while waitpid(-1, &st, WNOHANG) > 0`). Real-time signals (`SIGRTMIN`–`SIGRTMAX`) do queue and carry a value.
- Use **`sigaction()`**, not the old `signal()`, whose semantics vary between systems.

## Why handlers are dangerous

![The main code is inside malloc holding the allocator lock when SIGALRM arrives; the handler calls printf, which calls malloc and waits for the same lock, held by the same thread, so it deadlocks.](/figures/signals/deadlock.svg "The handler runs on the same thread as the code it interrupted.")

A handler is like an interrupt running inside your thread. It can interrupt:

- **a function that holds a lock**: `malloc` holding the allocator lock, `printf` holding the `FILE` lock. If the handler calls the same function, it waits for a lock that its own thread holds and will never release: **deadlock**.
- **a non-atomic update**: a linked list half-relinked, a buffer half-written. A handler that reads or modifies the same structure sees garbage.
- **`errno`**: a handler that calls `write` may overwrite `errno` between the main code's failing call and its check. Save and restore `errno` in handlers.

POSIX's answer is the list of **async-signal-safe** functions (see `signal-safety(7)`): functions that are reentrant or block signals internally. It includes `write`, `read`, `_exit`, `kill`, `sigaction`, `waitpid`, `open`, `close` and a few dozen others. It **excludes** `printf`, `malloc`, `free`, `exit` (which runs `atexit` handlers and flushes stdio), most of stdio, `pthread_mutex_lock`, and in practice any library code you don't control.

The same restriction applies after `fork()` in a multithreaded program: until `exec`, the child may only call async-signal-safe functions, for the same reason (another thread may have held a lock at the time of the fork).

## Safe patterns

![Five patterns: a flag the main loop checks; a self-pipe byte that an event loop polls; signalfd to read signals from a file descriptor; a dedicated thread looping on sigwaitinfo; language runtime APIs such as Go's os/signal, Python handlers and Node's process.on.](/figures/signals/patterns.svg "Make the signal synchronous, then handle it like any other event.")

1. **Set a flag.** The handler only sets a `volatile sig_atomic_t` (or a lock-free atomic) flag. The main loop checks it and does the work. Simple, but a blocking call needs to be interrupted (via `EINTR`) for the loop to notice.
2. **Self-pipe trick.** The handler `write()`s one byte to a non-blocking pipe, and the event loop watches the pipe's read end with `epoll`/`poll` alongside sockets. The signal becomes just another readable fd.
3. **`signalfd` (Linux).** Block the signals, create a `signalfd`, and read signal information from it like a file. No handler at all.
4. **A dedicated signal thread.** Block signals in all threads (set the mask before creating them), and have one thread loop on `sigwaitinfo()`, which returns synchronously when a signal arrives. That thread can safely lock, log and coordinate shutdown.
5. **Use your runtime's API**, which already does one of the above:
   - **Go:** `signal.Notify(ch, syscall.SIGTERM)` delivers signals on a channel.
   - **Python:** handlers registered with `signal.signal` run later, on the main thread, between bytecodes.
   - **Node.js:** `process.on('SIGTERM', ...)` runs on the event loop.
   - **Java:** shutdown hooks run on `SIGTERM`/`SIGINT`.

## Common signals

![Table: SIGINT from Ctrl-C terminates; SIGTERM from kill, systemd or Kubernetes terminates; SIGKILL terminates and can't be caught; SIGHUP when a terminal closes or to reload config; SIGSEGV/SIGBUS dump core; SIGPIPE terminates; SIGCHLD is ignored; SIGUSR1/2 are application-defined.](/figures/signals/common.svg "Their default actions explain many surprising process deaths.")

Notable behaviors:

- **`SIGPIPE`** kills a process that writes to a socket whose peer has closed, by default. Servers ignore it (`signal(SIGPIPE, SIG_IGN)`, or `MSG_NOSIGNAL` on sends) and handle `EPIPE` errors instead. Many language runtimes do this for you.
- **`SIGHUP`** originally meant "the terminal hung up". Daemons conventionally use it to **reload configuration** (nginx, HAProxy, sshd), and `SIGUSR1` to **reopen log files**.
- **`SIGSEGV`** is also used deliberately by runtimes: the JVM handles it to implement null-pointer checks and safepoints cheaply, and Go sends `SIGURG` to its own threads for asynchronous goroutine preemption.

## Graceful shutdown in containers

When Kubernetes stops a pod (or Docker stops a container), it sends **`SIGTERM`** to PID 1 in the container, waits for the grace period (30 s by default in Kubernetes, 10 s for `docker stop`), then sends **`SIGKILL`**.

Common problems:

- **PID 1 doesn't get default signal actions.** The kernel won't terminate a namespace's init process for a signal it has no handler for, so an app that relies on the default `SIGTERM` action simply ignores it and gets `SIGKILL`ed 30 s later.
- **A shell wrapper is PID 1.** With `CMD start.sh` (or the shell form of `CMD`), the shell receives `SIGTERM` and may not forward it to the real app. Use `exec` in scripts, the exec form `CMD ["app"]`, or a tiny init like **tini** (`docker run --init`).
- **No drain.** On `SIGTERM`, a server should stop accepting new connections, finish in-flight requests, flush buffers and exit, within the grace period. Load balancers may keep sending traffic for a few seconds after the pod starts terminating, so some apps wait briefly before closing listeners (or use a `preStop` hook).

### Use case walk-through: pods that always take 30 seconds to stop

Deploys are slow because every old pod takes exactly 30 seconds to terminate, and some requests fail during rollout.

1. **Observe.** `kubectl delete pod` hangs for 30 s. Events show the container was killed rather than exiting on its own.
2. **Find PID 1.** `kubectl exec <pod> -- cat /proc/1/cmdline` shows `/bin/sh -c ./server`. The shell got `SIGTERM`, didn't forward it, and (as PID 1 with no handler) didn't die either.
3. **Fix the entrypoint.** Use `ENTRYPOINT ["./server"]` (exec form), so the server is PID 1, and add tini for zombie reaping.
4. **Handle SIGTERM in the server.** On `SIGTERM` (via the runtime's signal channel or a sigwait thread), mark the readiness probe failing, wait ~5 s for endpoints to update, stop accepting connections, drain in-flight requests with a deadline, then exit 0.
5. **Result.** Pods stop in ~5–10 s, and no requests fail during deploys.

## Pitfalls

- **Calling `printf`, `malloc`, logging or locking in a handler.**
- **Not saving and restoring `errno`** in a handler.
- **Assuming one signal per event**: standard signals coalesce.
- **Ignoring `EINTR`** from blocking calls (or forgetting `SA_RESTART`).
- **Dying from `SIGPIPE`** in a network server.
- **Signals in multithreaded programs**: a process-directed signal goes to an arbitrary unblocked thread. Block signals everywhere and handle them in one place.
- **Relying on `SIGKILL` for cleanup**: it can't be caught, so plan for crash recovery instead of shutdown hooks alone.

> [!TIP]
> `grep Sig /proc/<pid>/status` shows a process's pending (`SigPnd`, `ShdPnd`), blocked (`SigBlk`), ignored (`SigIgn`) and caught (`SigCgt`) signal masks as hex bitmaps, which is handy for checking whether a process actually handles `SIGTERM`.

## FAQ

### What's the difference between SIGTERM and SIGKILL?

`SIGTERM` is a polite request: the process can catch it, clean up and exit (or ignore it). `SIGKILL` is enforced by the kernel and can't be caught or ignored. Well-behaved tooling sends `SIGTERM` first, waits, then sends `SIGKILL`.

### Is it safe to call exit() in a signal handler?

No. `exit()` runs `atexit` handlers and flushes stdio buffers, which aren't async-signal-safe. Use `_exit()` if you must terminate from a handler, or better, set a flag and exit from normal code.

### How do signals work with threads?

Each thread has its own signal mask. Signals caused by a thread (`SIGSEGV` from its own bad access) go to that thread. Signals sent to the process go to any one thread that doesn't block them. The usual approach is to block signals in all threads and handle them in a dedicated thread with `sigwait`, or use `signalfd`.

### Can I recover from SIGSEGV?

Rarely, and only in special cases: runtimes like the JVM deliberately trigger faults in known places (null checks, guard pages, safepoint polling) and handle them. For ordinary bugs, a `SIGSEGV` means memory is already corrupted, and the safe response is to log minimal information with async-signal-safe calls and exit.

### What's a zombie process?

A child that has exited but whose parent hasn't yet called `wait` to collect its exit status. It uses no memory, just a process table entry. A parent that ignores `SIGCHLD` and never waits accumulates zombies. In containers, an init process like tini reaps them.

## Key takeaways

- Signals are delivered **between arbitrary instructions** on the thread's next return to user mode.
- Only **async-signal-safe** functions are allowed in handlers. No `printf`, `malloc`, locks or `exit`.
- **Do almost nothing in the handler**: set a flag, write to a pipe, or use **`signalfd`/`sigwait`**/runtime APIs.
- Know the defaults: `SIGPIPE` kills, standard signals **coalesce**, `SIGKILL` and `SIGSTOP` **can't be caught**.
- In containers, make your app **PID 1 (or use tini)** and turn `SIGTERM` into a **graceful drain** within the grace period.
